- Sign-off is now decided by the decision service instead of blocking on a human (mw-decision-substitution W9, user ruling D). `.mw/decide.json` gains `signoff: auto|disable` (default `auto`, `mw decide sign --auto` / `--disable` persist it, an unreadable value keeps `auto` and surfaces as `signoff_error` without touching the other dps' config) and `mw decide sign` without `--conclusion` runs the automatic flow: `disable` writes nothing and clears the `done` gate's sign-off rules; `auto` asks the new `dp25-signoff-conclusion` decision point (P2 so it is on out of the box, one no-side-effect executor that only echoes `signoff:<conclusion>`, required `key`/`rows_total`/`rows_available`/`chain_ok`/`p0_open`, one `choice` question `continue|narrow|revoke` whose `instructions` carry the criteria) via `decide_for(..., intent="answer")` and records `signed_via: auto-decide`; when the transport is off, the dp is disabled, or confidence is below the effective `min_confidence`, it falls back to the caller's own inference (`--auto --conclusion X`) and records `signed_via: auto-llm` plus a `decide_fallback: <reason>` line, so the key can always close. - Added `mw decide ask` (mw-decision-substitution FIX-M): the human face of the decisions endpoint, so a person can actually ask `timi/jev-latest` instead of only feeding a pre-built request through `decide run`. `mw decide ask (--state <text|@path> | --state-file <path>) [--noul QID=TEXT ...] [--noul-criteria QID=true:TEXT;false:TEXT ...] [--choice QID=KEY[:TEXT][,KEY[:TEXT]...] ...] [--score QID=LOW,MID,HIGH ...] [--model MODEL] [--json] [--project DIR]` assembles the documented `{qid: {type, instructions, criteria?}}` map (a `--choice` option without `:TEXT` sends `criteria[key] = null`, a `--score` needs 2..10 ordered levels or the command exits 2, `--noul` omits the optional `criteria` key unless `--noul-criteria` supplies it, and the client's own `choices`/`labels` vocabulary is derived from the same flags) and sends it through the legacy `DecisionClient.decide(state, questions)` path - a human-authored request needs no dp authorization, so it carries no registry id and no authorization verdict (evidence row `dp=dp-human-ask`). - Added the cross-key red repair channel (xkey-repair-mechanism): a frozen-expectation change shipped by one key surfaces as a red in another key's suite with no owner, so the protocol lives in prose and gets hand-rolled per incident (the same repair was performed twice in two file shapes, and the second request's own citations were unverifiable line numbers). The new `autopilot/xkey.py` turns it into a machine loop: a below L3 round carries a registration machine line inside its mandatory `## Quality Gate Report` section (`cross_key_test=<path>::<test_id> owner=<key> handoff=registered not_fixed_by_this_key=True`) which the conductor parses from every L3 source and folds into the verdict-provenance sidecar under a new `registration` key; a project-level ledger (`.agenticdoc/_autopilot/xkey/ledger.json`, append-only history, lock-guarded read-modify-write, `tmp`+`os.replace`) dedups records by `(file, test_id, frozen-block sha)` and a ticket file per request is raised. Only a complete registration (a resolvable `(file, test_id)` and an `owner` that names a real key) produces a proposal - role values (`兄弟 key`/`PM`/`conductor`) and prose-only shapes escalate instead, by design and never by guessing. The frozen block is located mechanically (fail-line to test id to `ast` function to a module-level constant's assignment range, with byte-exact sha256 plus an EOL-normalized companion field), and the machine never widens it: a proposal touching the assertion body, an untouchable symbol, or another file is rejected before any write, so the target file's sha256 still equals its ticket-time value. Everything is off by default per project (`xkey_repair`), the conductor imports the module lazily so a disabled project never touches it, and the whole apply/verify/close chain (`xkey_verify_cmd`/`xkey_verify_timeout_s`) runs in the conductor by subprocess - a worker cannot hold a 630s suite under its idle watchdog - snapshotting the target bytes first and restoring them byte-for-byte when verification does not turn the red count green. Closure needs a five-item evidence bundle (old/new sha256, reason, `relaxed_assertion=False`, the targeted rerun command with its raw stdout, and the full-suite red count before/after) and writes both keys' closure annotations into the ledger row only - never into an affected key's tree, since a DONE key is not writable and a cross-key fix has no single owner.
