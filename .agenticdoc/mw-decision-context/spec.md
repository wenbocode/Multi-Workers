## §1 功能概述
### 1.1 目标
用最小充分业务材料替代重型决策本，把decide monitor从日志表转换为单次决策工作台。Jev只做选择，不生成文本；需要背景或候选时由发起Agent生成。
### 1.2 平台与用户
现有TypeScript agent-team-loop与Python multi-workers，独立Chrome/Edge应用窗口，PM、Worker及人工观察测试用户。
### 1.3 已确认的四DP
| DP | 模型输入 | 问题/选项 | 结果处理 |
|---|---|---|---|
| dp1-dispatch-type | 任务目标、要求、交付物原文；固定选项说明 | 仅coding/research/review | 沿用Jev原生返回，只消费类型，不加reason或risk第二问；派发是否自动改类型未新增授权 |
| dp2-checkpoint-split | 任务目标/要求/交付物、PM当前需要判断的原因与背景；可带worker执行情况（完成/剩余/阻塞/已尝试、时间预算），未派发或无自评不强求 | 保留decide_registry.json现有checkpoint_action问题、说明与narrow/split/direct-exec/escalate（收窄/拆分/直执/高风险给人） | 仅PM主动触发；Jev只选，PM落实，返回本身不自动终止、拆分、改写或直执，不代用户授权 |
| dp3-worker-clarify | 问题原文；背景：任务目标/现状/需要决策的原因/约束与影响；针对问题生成的处理候选及说明 | 从该问题的候选处理方式中选择 | 覆盖Worker→PM和PM→用户；提问Agent生成背景与候选并接收结果，不自动执行；用户偏好或授权仍问用户 |
| dp25-signoff-conclusion | 交付目标与确认验收条件/实际完成情况/验证证据（已验证、未验证分列）/未完成项及影响 | 可以收尾/继续完成/交用户确认，固定说明 | 可以收尾直接签收；继续完成交PM推进；交用户确认由PM提出具体待确认项 |

四DP全部沿用Jev原生选择返回，不另建业务JSON回答壳。原生协议中的usage/confidence等不要求删除，归本地日志，不变成额外业务问题。

### 1.4 背景生成原则
- dp1和dp2任务材料优先原文，不另生成分类指标或重复计数摘要；dp2背景由PM根据当前决策需要整理，可附真实worker执行情况。不做自动异常触发、research/review异常阈值或强制等待检查点自评。
- dp3由提出问题的普通LLM Agent按给定提示生成问题背景及候选；先有问题，候选不是预存事实答案。
- dp25由PM按给定提示生成四部分材料，不以完成任务数或PM完成声明替代证据。
- 默认用Agent已有上下文，不强制读一批文件；不足才补材料，未知显式标记，不编造事实。
- 模型输入与本地key/task/调用关联、hash、权限、采集状态等审计信息分离；关联信息无需占用业务判断材料。

### 1.5 monitor工作台
- 主表一行一次决策，key与DP下拉筛选；记录真实key/task关联，PM无task不强造。
- 主表保留业务信息：key/task、问题或摘要、DP、选择结果、状态；不铺来源/actor/answer_source/阶段/调用/usage/capture。
- 状态仅：处理中/处理完成/失败/旧数据无状态。处理完成指该次决策处理结束，不等整个key完成。
- 日志详情只默认展示时间与关联任务、发起角色、实际请求、实际响应、接收与处理结果、错误。来源/阶段/决策本/版本/hash等不再设页面栏目，内部必要关联与安全记录保留。[REVISED @ 2026-10-23，用户确认精简]
- 新记录点击展示单次DAG：key → 角色 → dp → 输入 → decide接口处理 → API请求 → 决策模型 → 返回结果 → 接收签收 → 行动反馈。
- 角色是发起角色PM/coding/research/review，不是dp1选中的角色；task放节点详情。
- 请求与返回显示实际捕获内容，代码块呈现；缺失/脱敏/省略明确，不重建原文。
- PM/Agent自动写回接收签收、采取的行动及结果，不需人工点已接收；模型返回不等已接收或已行动。
- 接收签收不同于dp25的key交付签收；自动反馈不扩大各DP执行权限。
- 重试独立记录关联前次，不覆盖；本轮不做整个key多角色总览DAG。
- 旧记录仍可筛选查询已有历史和日志，显示旧数据无状态，不展开或推断DAG。

### 1.6 测试工作台
- 首批仅dp1/dp2/dp3/dp25各一份完整、可直接校验的合成case，离线生成，页面读取可编辑。
- 包含对应简洁材料、选项及说明；不用填写旧schema身份/审计模板。
- 页面加载、case读取、编辑和本地校验不调用模型；只有显式观察提交调用。
- 与正式工作台相同的单次DAG和日志详情；显示测试身份及模拟/未执行的行动，禁止测试业务执行或生产签收。

### 1.7 不做什么
- 不重设计其他21DP、不生成其测试case，不删除通用vision/rag等真实角色能力。
- 不保留被本需求明确替代的四DP旧业务契约作为兼容分支；历史可读但不伪造新链路。
- 不在需求讨论阶段实施或删除源码；build/install、真实浏览器、真实Jev付费验收、共享服务切换及commit仍需明确许可。

## §2 业务约束
### 2.1 输入与决策边界
- 选项说明保留并随问题提供；不得用PM预选type/risk诱导dp1结果。
- dp25必要本地硬门在调用前检查；可以收尾直接写签收，不加PM二次批准；写失败报告失败而非已签收。
- Phase仍通过advance_phase门禁，签收不等手改phase或绕过证据要求。
- dp2和dp3选择交接与动作执行分离，自动回执只能记录真实发生的事。
### 2.2 安全与隔离
- 请求、返回、背景、候选、反馈、结构字段与日志展示全部适用known-secret安全输出；代码块与HTML转义不等脱敏。
- 不读生产凭证做验证；本地loopback fixture使用临时HOME、合成凭证和读前spy。
- 测试记录独立，不改生产授权、archive/signoff/triage；展示不触发模型或业务。
- 新持久化/公开输出沿用或补齐安全路径边界，不以id正则/hash seal豁免symlink、当前公开输出安全。
### 2.3 验证与性能
- 不先引入任意字节上限或性能SLA；设计根据真实样例和现有transport预算定义可测边界，超预算/缺材料明确失败，不静默裁掉关键判断材料。
- 新行为必须实现前正确RED→GREEN；修后mutant、行为回放、collection失败分别披露，不替代test-first证据。
- 源码、DOM shim、本地HTTP、真实浏览器、真实Jev验证层分列，局部绿不累计成整体AC完成。
