# Decision 不可用时的策略化降级与任务连续性设计（参考草案）

> 状态：PROPOSAL，仅供评审；不是已批准需求、实现说明或运行授权。
>
> 日期：2026-11-10。
>
> 关联：`mw-dp-consolidation`。本文不覆盖该 key 已锁定的 SPEC、53AC、已批准设计和当前实现计划。采纳涉及的受控变更、精确写面和验收增补须另行确认。
>
> 用户需求：决策模型不可用时，可按当前配置默认处理，例如直接放开、阻止，或交当前 Agent 的 LLM 自行判断，类似 Agent 的预批准模式；同时避免局部决策故障拖停全部任务。

## 1. 结论与推荐

将决策系统从“所有调用失败统一阻塞并等人工”，优化为：

**决策结果与故障处理分层；按事项配置降级；工程执行隔离故障；权限、预算、证据、锁和执行安全保持硬约束。**

推荐支持五种处理策略：

| 策略 | 用户含义 | 实际语义 |
|---|---|---|
| `allow` | 帮我批准／直接放开 | 在已授予的范围内，按明确默认动作继续；记录为策略预批准，不冒充模型回答 |
| `deny` | 直接阻止 | 拒绝本次操作，不执行；不取消目标、不默认结束整个项目 |
| `agent_llm` | 交当前 Agent 自己决定 | 由当前合法主体的执行 LLM，使用原材料与候选进行有界自决；不偷偷换外部 decision provider |
| `human` | 转给我 | 保存具体事项、影响及可选动作，等待受权用户作出本事项决定 |
| `hold` | 等决策模型恢复 | 暂停本事项，保存恢复信息；其他无依赖工作继续 |

最重要的限制：

1. `allow` 是用户对某类操作的**预授权**，不是模型故障产生的新权限。
2. 普通项目配置只能在已有授权范围内选择策略，不能通过编辑 JSON 自授权限。
3. 任何策略都不能绕过原有文件权限、角色、claim、独占写面、预算、用户停止及必需验证。
4. 需要独立判断的 QG、签收等事项，不能把执行者自决或一般“全部批准”配置自动等同于合法独立审核。
5. 没有有效策略或策略不适用时，默认 `hold`，不是默认放开。

本文建议先在普通工程编排与 Worker 可达性判断落地策略化降级；正式签收、阶段关闭及受控恢复按明确事项授权逐步接入。

## 2. 现状与问题

### 2.1 已有事实

- 主工作区仍是旧编号 DP；八入口新版在 `.tmp/dpc/implementation-worktree`，尚未回移部署。
- 当前项目 decision 默认关闭。用户已明确：disabled 不应阻止已有授权内的开发、验证、证据和审核工作。
- 专用 decision 通道固定为 Timi `/v1/decisions`、`jev-latest`；当前执行 Agent 的模型不是专用 decision 模型的同义词。
- 2026-11-10 的一次真实合成请求返回 HTTP 200、有效 `jev-latest` 答案，耗时约 1.156 秒。这只能证明当时接口可用，不代表持续可用性或复杂决策正确率。
- 现设计要求无有效裁决时阻塞对应动作；工具提示仍倾向统一“等待人工”。
- 隔离实现中，Worker 的 `dp-w-check-task` 不可用会锁住后续普通工具调用，并在本轮结束时按不完整执行收尾，基础设施故障可能扩大为任务失败。

### 2.2 要解决的问题

1. JEV 单点故障不应让所有独立工程任务停工。
2. 用户应能选择：哪些事项预批准、哪些拒绝、哪些交执行 LLM、哪些必须等人或等服务。
3. 任务失败、决策服务阻塞、用户拒绝三者应可区分。
4. 不因降级伪造 JEV 回答、decision_id、签收、执行或完成事实。
5. 服务恢复后不重复执行已经通过降级完成的动作，也不盲目重发结果未知的请求。

## 3. 范围与非目标

### 3.1 包含

- 八入口的不可用处理策略、适用性与默认动作约束。
- 主动关闭、服务故障、输入错误、权限拒绝和执行结果未知的分类。
- PM／Worker 的故障隔离、保存产物、受控结束和接续。
- 可信预授权、当前 Agent LLM 自决、人工接管和等待恢复。
- 结果来源、历史展示、幂等、状态有效性和故障验收。

### 3.2 不包含

- 本文不启用 decision、不修改凭证或运行配置、不切换实际模型。
- 不自动增加备用 provider，不将聊天接口伪装为原 `/v1/decisions`。
- 不取消既有机器硬门、权限、预算、用户停止和独立审核要求。
- 不自动扩大写面、提高硬预算或修改冻结 AC。
- 不将本参考草案当作当前隔离实现安全缺陷的修复。
- 不修改 pi 核心；实现继续限定在扩展与 MW 后台的合法接口内。

## 4. 故障分类：不是所有失败都能“默认批准”

| 分类 | 例子 | 是否进入不可用降级 |
|---|---|---|
| `disabled` | 用户主动关闭专用 decision | 按单独的 disabled 策略处理；不假装发生接口故障 |
| `transport_unavailable` | 超时、DNS／连接失败、429、5xx、接口不存在 | 可以，需满足预授权及重试／时间预算 |
| `credential_unavailable` | 缺 key、401、403 | 可以进入明确覆盖凭证故障的策略；不自动换 key 或修改凭证 |
| `answer_unusable` | 缺回答、非法选择、缺 basis、低置信度、协议不匹配 | 只有策略显式覆盖才可降级；保留异常事实 |
| `input_invalid` | 材料缺失、候选非法、超输入预算 | 不按服务故障直接放行；允许授权内修正材料后重验 |
| `authorization_denied` | 角色错误、撤权、claim 冲突、越写面 | 不允许降级放行；原硬拒绝保持 |
| `hard_check_failed` | 预算不足、验证失败、缺必需签收／证据 | 不允许降级豁免；先修复或取得合法授权 |
| `explicit_business_result` | 模型明确 reject／need_fix／continue | 不是不可用；不能借 fallback 改判批准 |
| `outcome_unknown` | 请求或动作已开始，崩溃后不知是否完成 | 先对账；不启动另一条降级执行链 |

补充：模型低置信度与 HTTP 故障应分别配置。不能把“模型对风险不确定”统一解释成“既然失败就批准”。

错误默认采用白名单分类；未知错误进入 `hold` 并展示原因。

## 5. 策略模式与授权模型

### 5.1 两组独立配置

- `on_disabled`：专用模型主动关闭时如何处理。
- `on_unavailable`：启用后遇到指定故障时如何处理。

关闭服务不等于修改审批规则。已存在明确授权、无需新判断的工程工作不受影响；本来需要有效批准的事项，仍需合法降级或保持阻塞。

### 5.2 对用户提供的简化模式

| UI 模式 | 示例用途 | 展开后的策略 |
|---|---|---|
| 严格模式 | 高风险自动化 | 新决策不可用时 `hold` 或 `human` |
| 工程自决模式（推荐） | 日常开发、测试与编排 | 合法工程事项 `agent_llm`；审批／签收保持严格 |
| 受限预批准模式 | 明确希望故障时继续的低风险工作 | 已列事项 `allow`＋具体默认动作＋授权范围 |
| 全部阻止模式 | 敏感环境 | 本次受门控操作 `deny` |
| 自定义 | 项目专门要求 | 按 DP、事项、错误类型细分 |

不提供无边界的“绕过所有检查”。界面如显示“帮我批准”，必须同时展示它批准的 DP／事项、动作、有效期、写面和预算边界。

### 5.3 三层职责

1. **策略选择配置**：用户想选哪种处理方式，可由项目配置表达。
2. **可信授权来源**：证明谁允许了哪类降级；复用已批准的真实用户授权／受控操作来源验证，不新增一份可任意编辑的 grant 账本。
3. **执行时硬检查**：判断这一次是否还在范围内，不能被策略配置覆盖。

仅有 `authority_ref` 字符串或 `preapproved: true` 不足以建立授权。来源、对象、版本、权限范围、撤销状态与真实主体必须可核。

未授权的请求写入提示词、任务卡或证据文件，不得修改有效策略。Worker 不得修改自己的降级授权。

### 5.4 策略匹配

候选策略按“具体事项规则 → DP 规则 → 项目默认”选择；随后与全局／组织硬约束及授权范围取交集。

- 更具体配置不能扩大上层限制或用户授权。
- 同优先级冲突、无匹配、来源非法、授权过期或撤销时，保持阻塞并报告原因。
- 策略变化不追认以前失败的请求、不重写历史，也不自动重放。
- 对结果未知或已经执行的事项，先对账，不能因策略切换再次执行。

## 6. 每种策略的精确定义

### 6.1 `allow`：策略预批准

适用前提：存在明确预批准授权；材料足够核验边界；默认动作合法且没有语义歧义；硬检查全部通过。

- 例如 Worker 可达性默认 `continue`，只允许继续原任务，不重置超时或扩权。
- 例如特定 stage-start 默认 `approve`，仍需原启动条件成立。
- 对动态候选必须绑定确切候选 ID 和材料版本，不能默认选第一项。
- `dp-route` 只能给出预配置目标入口，不产生业务批准。
- 没有可定义默认动作的事项，不允许只凭 `allow: true` 推进。

记录 `source=policy` 与真实授权引用。模型置信度为未提供，不能填 1.0。

### 6.2 `deny`：拒绝本次操作

- 零业务执行，明确拒绝理由和策略来源。
- 不自动删除产物、取消 key、判项目失败或关闭 stage。
- 不等于模型返回业务 reject；两者来源不同。
- Agent 可做无副作用收尾和不依赖该操作的其他已授权工作。

### 6.3 `agent_llm`：当前 Agent 自决

这里的 LLM 是当前合法 PM／Worker 的执行模型，不是后台静默换用另一家 decision 服务。

流程：

1. 当前请求被合法分类为可降级。
2. 核对当前 Agent 身份、角色、原任务、授权、材料与候选。
3. 向当前窗口发送结构化自决请求，或由工具返回明确的自决材料要求。
4. Agent 给出结构化选择、理由、材料引用和未知事实。
5. 独立的机器校验器检查选择集合、角色、作用范围和执行前置。
6. 合法结果交原受限执行器；失败或当前 Agent 也不可用时，进入预先配置的终结策略。

约束：

- PM 不代 Worker 作自身可达性判断，Worker 不因 fallback 获得 PM 专属权限。
- 不能从失败 reason 推断选择，不默认批准，不自动缩减目标。
- 不复用 JEV 的 confidence 字段；自决不是专用模型的独立审核结论。
- 原模型同次 choice＋basis 合同保留；fallback 的理由单独标注为当前 Agent 提交，并引用原材料，不冒充原生 JEV basis 回答。
- 必须设置有限时间／次数；消耗计入现有预算，不授予新预算。
- 不递归调用不可用的同一个 DP 来批准自身 fallback。
- 不调用另一个 LLM 去批准“是否交当前 LLM”，避免无限降级链。
- 自动后台没有可绑定的当前 Agent 时，不伪造其身份；使用明确终结策略。

推荐终结策略仅允许 `hold`、`human`、`deny`。Agent 自决失败后不再自动转为 `allow`。

### 6.4 `human`：受权人工处理

保存具体待决问题、原材料、已失败尝试、影响、候选和授权边界，等待真实用户通过受控入口响应。

- 通知不是批准，普通工具 confirm 也不自动证明真人来源。
- 人工批准只覆盖本事项，并仍受机器硬门约束。
- 人工拒绝、没有响应和通信失败分别展示。
- 人工变更范围／预算／验收时，走对应受控变更，不用一般答复代替授权。

### 6.5 `hold`：暂停本事项并等待恢复

- 保留 request／matter／策略版本和必要材料引用。
- 不默认终止所有 Worker，不把等待记作已完成或业务拒绝。
- 独立任务继续；直接依赖该判断的后继等待。
- 到期或健康恢复只触发复核，不自动批准／执行。
- 重新判断前核材料、授权、版本、预算和实际效果。

## 7. 八入口推荐矩阵

下表是建议默认值，需用户确认；不是当前运行设置。

| 入口 | 推荐不可用策略 | `allow` 的适用限制 | 不能被豁免的内容 |
|---|---|---|---|
| `dp-w-type` | 原派发为建议时保留合法显式 type；需要选择时 `agent_llm` | 只接受预配置或合法任务卡类型，不猜未知类型 | 图像能力、工具角色、写面与派发冲突检查 |
| `dp-pm-steer` | `agent_llm` | 原方案继续必须有具体有界动作；不能自动把 `narrow` 当批准 | 目标、验收、在途 Worker 协调及权限预算 |
| `dp-w-check-task` | 当前 Worker `agent_llm` | 可预批准 `continue`，但限原任务、原工具及预算 | 真实不可达条件、超时、权限、用户停止 |
| `dp-auto` | `agent_llm` | 默认候选须确切绑定原候选集合／材料版本 | 不代固定审批、不发明候选或新授权 |
| `dp-route` | 当前 PM `agent_llm` | 只配置目标入口，不产生业务选择 | 主体资格及目标 DP 材料要求 |
| `dp-QG` | `hold` 或受权独立人工审核 | 一般“批准所有”不适用；预先存在有效同事项质量证据可依法复用 | 必需验证、阻断项、独立性和证据充分性 |
| `dp-gate-approve` | 按 gate 事项细分，默认 `hold` | 已授权且所有前置成立的具体事项可策略预批准 | 启动／关闭／恢复各自前置、停止／撤权、预算与证据 |
| `dp-sign-key` | `hold` 或受权人工签收 | 不以普通 `allow` 直接制造 finalize；如需策略签收，须单独批准签收来源合同 | 真实交付、必需 QG／验收、当前证据、身份与适用范围 |

解释：

- 提供 `allow` 不等于每个 DP 都能无条件使用。
- `agent_llm` 只替换可授予的判断主体，不替换证据或机器检查。
- 正式签收若将来允许 Agent／policy 作为认可来源，必须显式改变现有“仅有效模型 finalize”合同及 validator；不能仅调整 fallback 配置。

## 8. gate 事项分层

| 事项 | 可建议的降级 | 关键条件 |
|---|---|---|
| 授权内普通工程组织 | `agent_llm`；受限 `allow` | 任务目标、写面、并发和预算未变化 |
| stage 启动 | 受限 `allow`／`agent_llm`／`hold` | 已有明确预授权、必需材料和机器检查；不授新预算 |
| stage 达标关闭 | 默认 `hold`／`human` | 必需交付、适用签收及跨 key 集成验收齐备；不批准下阶段启动 |
| 软轮次追加 | 受限 `allow`／`agent_llm` | 明确追加量、理由、结束判据及累计硬预算，不无限续跑 |
| goal／冻结 AC 变更 | 默认 `human` 或 `hold` | 明确具体变更授权；不能通过故障策略减少交付承诺 |
| 跨 key 修复 | 默认 `hold`，可限定预授权 | 目标 key、文件、动作、claim、独占面和实际 writer 边界完整 |
| 工程原因 halted 恢复 | 受限 `agent_llm`／`hold` | 原因消除证据、恢复授权、预算和真实效果对账 |
| 用户停止／撤权 | 禁止普通 fallback 放行 | 取得新的明确恢复授权 |
| H12 自动熔断恢复 | 默认 `hold`／受控人工 | 只能通过独立受权恢复通道；普通熔断链不能自批解锁 |

不通过字符串 `risk=low` 判断是否可放行。事项类型、动作效果、目标路径、授权和原硬检查共同决定适用性。

## 9. 建议配置形式

建议在现有配置体系下增加独立可选策略文件，例如 `.mw/decision-fallback.json`，避免随意扩展已有冻结配置。最终落点须结合既有配置约束评审。

以下仅是说明性示例；**当前代码不支持，不应直接复制当作已生效配置**。

```json
{
  "schema_version": 1,
  "default": {
    "on_disabled": "hold",
    "on_unavailable": "hold"
  },
  "rules": [
    {
      "id": "worker-continue-within-original-task",
      "dp": "dp-w-check-task",
      "authority_ref": "user-authority-reference",
      "match": {
        "actor": "current-worker",
        "matter_class": "ordinary-engineering"
      },
      "on_disabled": "agent_llm",
      "on_unavailable": "agent_llm",
      "eligible_failures": ["transport_unavailable"],
      "agent_llm": {
        "max_attempts": 1,
        "on_failure": "hold"
      }
    },
    {
      "id": "preapprove-authorized-stage-start",
      "dp": "dp-gate-approve",
      "authority_ref": "stage-start-preapproval-reference",
      "match": {
        "matter_class": "stage-start",
        "scope_ref": "authorized-stage-scope"
      },
      "on_disabled": "hold",
      "on_unavailable": "allow",
      "eligible_failures": ["transport_unavailable"],
      "default_action": {"choice": "approve"}
    },
    {
      "id": "formal-signoff-waits",
      "dp": "dp-sign-key",
      "on_disabled": "hold",
      "on_unavailable": "human"
    }
  ]
}
```

示例中的授权引用必须能回溯到真实受权来源；没有该来源，第二条规则不能生效。人工签收能力也须先有单独获批合同与实现。

配置验证要求：

- 拒绝未知策略、未知 DP、缺省动作非法、匹配歧义和自循环 fallback。
- `allow` 必须有明确默认动作及授权范围。
- `agent_llm` 必须有限额、终结策略和可核当前主体。
- 凭证错误／答案不可信等特殊类别须显式列入，不能隐含覆盖。
- 配置缺失默认严格；非法规则不静默降成放开。
- 配置与授权版本参与结果有效性判断；高权限规则不能由 Worker 自己写入并采用。

## 10. 运行架构与流程

### 10.1 逻辑模块

| 模块 | 职责 |
|---|---|
| failure classifier | 区分服务故障、材料问题、权限拒绝、业务结论及结果未知 |
| policy resolver | 按 DP／事项／故障类型匹配策略，验证授权来源与冲突 |
| resolution coordinator | 在原文件驱动机制内保存本事项降级状态，不新建中央调度器 |
| agent self-decision adapter | 向合法当前 PM／Worker 提交有界结构化自决 |
| action validator | 核选择、版本、角色、授权及机器硬门；不给模型自行关闭检查的能力 |
| existing executor | 执行原受限动作并保留真实结果 |
| recovery／projection | 展示来源、等待与实际效果，恢复时对账，不合成历史 |

### 10.2 主流程

```text
准备原业务材料与真实身份
  → 先验原权限／角色／硬条件
  → 专用 decision 关闭？
      是：匹配 on_disabled
      否：调用 JEV，按现有有界重试取得结果
          有效业务结果：沿原路径消费，不调用 fallback 改判
          无有效结果：分类
  → input_invalid：授权内补材料或保持阻塞
  → authorization_denied / hard_check_failed：原拒绝保持
  → outcome_unknown：先对账，不另开执行链
  → eligible unavailable / disabled：匹配与核验策略
      allow：生成策略预批准处理结果
      deny：拒绝本次操作
      agent_llm：当前合法 Agent 有界自决
      human：待受权人工结果
      hold：保存并等待恢复
  → 对可执行结果重新检查当前版本／claim／授权／预算／写面
  → 原执行器执行
  → 记录真实 action／settled／task outcome
```

### 10.3 结果字段分层

不要把 JEV 的 `available=false` 改写成 `true`。建议新增版本化的处理结果层：

```json
{
  "schema_version": 1,
  "primary_result": {
    "available": false,
    "reason": "timeout"
  },
  "resolution": {
    "id": "locally-generated-resolution-id",
    "source": "policy",
    "strategy": "allow",
    "status": "resolved",
    "choice": "approve",
    "authority_ref": "verified-authority-reference",
    "policy_version": "policy-version",
    "matter_version": "reviewed-matter-version"
  },
  "effect": {
    "status": "not-started"
  }
}
```

这是接口概念草案，不是现有响应合同。`resolved` 不等于已执行，`approve` 不等于已通过硬检查。

- 原模型真实请求有真实 decision_ref 才关联；没有模型决定时不造 JEV decision_id。
- resolution_id 是本地处理事件身份，与模型 decision_id 分开。
- 原账本追加独立、版本化的 resolution 事件；协调文件只存引用与状态，不另造第二套决策权威账本。
- `agent_llm`、`human`、`policy` 均保存真实来源，不混入 JEV 的答案／概率字段。
- 现有工具的 `available=false → stop` 合同需要一并迁移；不能仅让 caller 忽略失败响应并继续。
- 未升级的调用方按原严格逻辑处理，不静默采用新结果。

## 11. PM／Worker 的任务连续性

### 11.1 PM

PM 把任务分为：

1. **不依赖本决策的已授权工作**：继续实施、测试、取证、审核与组织。
2. **直接依赖本决策的动作**：依据合法 resolution 继续，或保持本事项阻塞。
3. **依赖该动作产物的后继**：等待依赖满足，不把未批准当已完成。

一个签收阻塞不应停止另一独立 key 的测试；一个 Worker 自决失败也不应停止其他合法在途 Worker。

### 11.2 Worker

用明确的受限模式代替“一次 decision 失败后所有工具无差别锁死”：

- `active`：正常执行原任务。
- `awaiting-resolution`：暂停依赖该判断的工作；禁止被门控副作用。
- `safe-finalizing`：仅保存当前允许产物与固定报告，记录完成／未完成／阻断和接续位置。
- `ended`：按真实结果结束本次执行。

安全收尾必须是窄接口和精确写面：不能以“保存产物”为由运行任意 bash 或修改任务外文件；沿用已有 watchdog／硬截止，不无限等候。

推荐先保留现有队列终态集合，增加 typed `end_reason=decision-unavailable`、`retryability` 和 `resume_ref`，避免立刻迁移所有状态消费者。界面明确显示“基础设施阻塞，目标未判失败”。现有终态如何映射须统一 launcher、PM、monitor 后再定。

若当前 Worker LLM 仍可用，`agent_llm` 就地完成自决；如无法在本次执行预算内解决，安全收尾并由 PM 后续接续，不新增同步等 PM 指令链。

### 11.3 独立证据与正式交付

decision 故障期间可以完成代码、测试和审核报告，但正式 QG／签收／stage 关闭仍按适用合同处理。界面要允许表达：

- 实现完成；
- 验证通过；
- 正式判断等待服务／受权人工；
- key／stage 尚未关闭。

不把“没拿到签收”错误显示为“代码未完成”，也不把“测试绿”显示为“已签收”。

## 12. 重试、恢复、并发与熔断

- 保留原专用通道的有限重试，不自动换模型或端点。
- 统一一次事项的总时间预算，避免 HTTP retry × Agent 重试 × PM 重派相乘。
- 重复调用者复用同事项协调状态，不能各自请求 fallback 并重复执行。
- 先锁内核状态与版本，再记录处理意图；网络和 LLM 调用不持共享队列锁；返回后重核。
- 原模型已经产生有效业务结论时不启 fallback；原动作结果未知时先对账。
- 原请求确定失败后采取 fallback；迟到的原回答保留为迟到事实，不覆盖已提交的处理来源或再执行动作。
- 服务恢复只是事件：核本事项是否已经 resolved／executed、材料是否变化，再决定是否重试。
- 对已经通过 fallback 完成的事项不自动补一次 JEV 批准；需要事后复核的事项单独记录，不倒填当时来源。
- 软故障熔断只限制专用 decision 请求频率，不自动终止全部工程工作。
- 原 H12 安全熔断与用户停止不能被一般故障策略解除。恢复仍走独立受权通道。
- HTTP／文件／ledger 不是跨文件事务。崩溃窗口保留 `unknown` 并核实际对象；不承诺无条件 exactly-once。

## 13. 安全与可观察性

### 13.1 必须保持的边界

- 配置不是授权，模型选择不是权限，fallback 不是硬门豁免。
- 不因所有 provider 都不可用而无条件 allow。
- 不把真实业务 reject、证据不足或低置信度隐匿成网络故障。
- 不允许任务卡／网页／代码中的注入文本调整策略或降级身份。
- 不在错误、策略引用、材料引用或报告中泄露 key。
- 人工、policy、Agent 自决的产物分别校验身份与出处。
- 对签收来源的扩展必须更新 writer、validator、phase gate 与 UI，不能只补一个标签。

### 13.2 UI／日志建议

每个事项显示：

- 专用模型状态：关闭／可用／超时／限流／答案不可用；
- 实际处理策略及生效规则；
- 结果来源：JEV／当前 Agent／预批准策略／人工；
- 授权范围与当前硬检查；
- 请求、处理选择、业务执行、结算、任务完成的独立状态；
- 等待对象、下一复核条件、是否可接续及失败原因。

例如：

```text
原决策：JEV timeout
处理：按规则 worker-self-decide 交当前 Worker LLM
结果：continue（当前 Agent 自决，非 JEV 回答）
授权：原任务范围不变；预算与写面检查通过
执行：已完成一次原授权工具调用
任务：仍在运行
```

建议测量：各故障类型数量、策略命中／拒绝次数、阻塞时长、独立任务继续数、重复执行数、越权数、人工接管数与恢复次数。本文不虚设性能 SLA 或实际预算值。

## 14. 验证与验收建议

采用 faux provider、隔离项目／HOME、受控时钟和实际生产 writer；不用真实 key 作为日常测试依赖。

| ID | 场景 | 应观测结果 |
|---|---|---|
| F-01 | 无策略时 JEV 超时 | 本事项 hold，零默认放行；独立任务继续 |
| F-02 | disabled＋授权内工程自决 | 不请求 JEV，当前合法 Agent 可处理；不生成模型决定 |
| F-03 | disabled 无签收授权 | 不能签收，不因关闭开关自动扩大权限 |
| F-04 | allow＋有效预授权＋全部硬检查通过 | 精确默认动作一次，来源 policy，真实 action 单独记录 |
| F-05 | allow＋撤权／越写面／预算不足 | 零业务动作，具体阻断可见 |
| F-06 | 动态 auto 缺默认候选或材料版本改变 | 不默认第一项，不复用过期默认动作 |
| F-07 | Agent 自决合法／非法候选／角色冒充 | 仅合法当前主体和集合内选择可进入执行检查 |
| F-08 | Agent 也不可用或超预算 | 按终结策略收尾，无递归调用或静默 allow |
| F-09 | Worker 可达性服务故障 | 无关 Worker 继续；当前 Worker 能窄权限落盘交接，不伪 done |
| F-10 | deny | 本次操作拒绝；目标、产物和项目不被自动取消 |
| F-11 | 429／401／低置信度分类 | 只命中显式覆盖的故障规则，不误用统一放开 |
| F-12 | 输入非法／硬检查失败／模型明确 reject | 不可借 fallback 改判放行 |
| F-13 | 同事项并发原调用／fallback／恢复事件 | 一个有效处理 owner，零重复动作，未知窗口先对账 |
| F-14 | fallback 已执行后 JEV 恢复或迟到 | 不追加重复批准／执行，不改写原来源 |
| F-15 | QG／签收／stage 关闭必需证据缺失 | 任何普通预批准或 Agent 自决均不能豁免 |
| F-16 | H12 或用户停止 | 普通 fallback 不解锁；恢复必须独立合法授权 |
| F-17 | 配置伪造／Worker 改配置／提示注入 | 不产生新 grant，非法策略明确拒绝 |
| F-18 | 原工具协议和新 resolution 协议混用 | 不把 available=false 当默认成功；旧消费者严格拒绝不支持结果 |
| F-19 | 暂停后 goal／授权／契约实质变化 | 原处理结果失效或需重审，不受影响证据可复用 |
| F-20 | 历史与安全投影 | 原历史字节不变；未知与 null／[]不混淆；秘密／脚本不泄露执行 |

除“未越权”外，必须验收“有授权时确实能够继续、无关任务不停止、失败可交接、恢复不重复”。

## 15. 与现有设计的兼容和受控变更

本文不是不改变语义的小补丁。采纳前至少须明确：

1. 原 AC-012／043 等“不可用时受门控动作保持阻塞”，应区分原模型失败与另有合法预授权的处理结果；不能声称原正文天然已经允许 fallback 放行。
2. 原 choice＋basis、同次签收和真实主体约束继续保留；fallback 使用独立来源合同。
3. `ask_decision` 的失败指令、工具返回类型、PM／Worker 消费器和生命周期要联合迁移，不能只改提示词。
4. 默认只扩普通工程处理；正式 QG／签收／H12 的替代来源另行确认，不默认纳入“一键批准”。
5. 当前已确认的身份／dry-run／跨 key 写边界／并发／秘密处理问题仍需修复；新增策略不能掩盖这些缺陷。
6. 不为兼容保留可运行旧 DP 别名；历史只读保持。

## 16. 实施分组与并行性分析（供后续计划参考）

本文不启动实施、不创建 worker，也不改当前36任务／53AC。若采纳，建议按范围判断新 key 或原 key 的受控变更，不直接追加无追踪代码。

可并行单元：

- A：失败分类与策略纯模块、配置验证及测试。
- B：当前 Agent 自决材料／响应协议和角色校验及测试。
- C：UI／历史的来源与等待状态只读投影及测试。

共享资源与必须串行的部分：

- 请求／resolution／执行接口先锁定，A／B／C 才可独立编码。
- `decision-tool.ts`、`worker-mode.ts`、`conductor.py`、CLI 与签收 validator 是共享边界，同一文件同时只一个 writer。
- 正式签收来源变更必须先确认合同，再联合 writer／validator／phase gate 验证。
- 并发／崩溃／跨语言完整链测试在接口稳定、源码冻结后执行。
- 活配置与可信授权不纳入编码 worker 写面；安装部署另行授权。

建议顺序：

1. 确认策略范围与默认值，解决原 AC 语义变化。
2. 先实现纯策略及来源校验，默认严格、不启运行。
3. 接入普通工程与 Worker 自决／安全收尾，验证连续性。
4. 接入 gate 事项化策略；特殊正式审核／签收单独评审。
5. 完成故障矩阵、回归、独立审核、完整检查及受控部署。

## 17. 评审需确认的四个问题

1. 是否接受五策略：`allow / deny / agent_llm / human / hold`？
2. 是否采用“普通工程默认交当前 Agent，自带硬检查；正式签收／高风险恢复默认严格”的推荐配置？
3. “帮我批准”是否限定于明确预授权的具体事项，还是希望额外支持正式 QG／签收替代来源？后者需要单独定义独立性和证据合同。
4. 当前 Agent 也不可用时，默认 `hold` 还是 `human`？两者都不自动退成 allow。
